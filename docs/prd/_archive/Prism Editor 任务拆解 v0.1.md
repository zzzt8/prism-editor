# Prism Editor 任务拆解 v0.1

## P0：必须做，不做就没有第一阶段闭环

P0 的目标只有一个：**让你能稳定地把 1 条真实图像链路，从“纯代码/试错”迁到 Prism Editor，并能复用、调试、交付。** 你现在最痛的是不稳定、试错成本高，同时第一阶段核心能力又明确是节点编辑、参数面板、预览、模板复用、输入输出映射，所以 P0 必须围绕这几个点收口。 

### P0-1. 冻结核心数据契约

先定三套对象，不允许边写边长：

* `EditorDraft`：编辑态工作流
* `Template`：可复用模板
* `PublishedConfig`：发布后的运行配置

每套对象都要明确：

* 基本信息
* 节点列表
* 连线关系
* 输入输出定义
* 参数暴露方式
* 版本字段
* 元数据字段

**完成标准：**

* 三套类型结构文档化
* 前后端都只认这三套对象
* 不再出现“编辑态字段直接泄漏到发布态”的情况

这项必须排第一，因为你自己最担心的就是“数据结构越来越乱”。

### P0-2. 跑通 1 条最核心业务链路

先只打磨你已经定义的那条：
**输入 → 抠图 / 缩放 / 遮罩 / 合成 / 导出 → 输出效果图与生产图纸。** 

任务包括：

* 明确这条链路需要的最小节点集合
* 用 Prism Editor 完整搭出一版
* 保证能重复执行
* 保证输出结果满足真实业务可交付标准

**完成标准：**

* 这条链路能在编辑器中完整配置
* 至少完成 3 次重复运行验证
* 输出结果可直接进入“发用户 / 发厂家”的真实流程

### P0-3. 做稳最小系统节点集

第一阶段节点来源你已经定了：先做系统节点，后面再谈插件机制。那 P0 就不要扩散，只做支撑核心链路的节点。

建议首批系统节点：

* Load Image
* Resize / Transform
* Mask / Apply Mask
* Composite
* Preview
* Export
* Input / Output Adapter
* Empty / Placeholder Input

**完成标准：**

* 每个系统节点都有统一 definition
* 每个节点都能在面板中配置参数
* 每个节点都有最小测试样例
* 首条核心链路只依赖系统节点即可跑通

### P0-4. 完成编辑器最小闭环

你定下来的核心能力里，真正能闭环的最小集合应该是：

* 节点编辑
* 参数面板
* 预览
* 模板复用
* 输入输出映射
* 保存草稿
* 最小发布能力

其中后两个是我帮你补的“隐含 P0”，不然模板和稳定运行都落不了地。你的目标里已经包含“已发布工作流可稳定运行”，所以发布不能没有。

**完成标准：**

* 可创建工作流
* 可拖拽/连接节点
* 可编辑参数
* 可预览中间结果或最终结果
* 可保存草稿
* 可保存为模板
* 可发布为运行配置

### P0-5. 输入输出映射规范化

这个是 Prism Editor 从“画布工具”变成“工作流产品底座”的关键一步。你已经明确第一阶段希望未来运行页可以弱化，甚至先转成 API 方式接入平台，所以输入输出映射要先定义干净。

任务包括：

* 定义输入类型
* 定义输出类型
* 定义必填/选填
* 定义默认值
* 定义可暴露给用户的参数
* 定义内部参数与外部参数边界

**完成标准：**

* 一个工作流能清楚声明“我要什么输入，产出什么输出”
* 发布后的配置能被外部系统消费
* 输入输出映射不依赖编辑器内部状态

### P0-6. 最小调试能力

你自己已经把“调试体验差”列为核心风险之一，所以这不是附加项，是 P0。

建议最小调试能力：

* 节点执行状态提示
* 节点级报错信息
* 节点输入/输出快照查看
* 执行链路高亮
* 一键重跑当前工作流

**完成标准：**

* 出错时能定位到具体节点
* 能看见节点收到什么、吐出了什么
* 能区分“参数错误 / 输入缺失 / 执行失败”

### P0-7. 模板机制落地

你把模板复用列进了前五能力，那它就不能只停留在“复制 JSON”。

任务包括：

* 工作流另存为模板
* 从模板创建新工作流
* 模板基本信息管理
* 模板适用场景说明
* 模板输入输出 schema 固化

**完成标准：**

* 至少有 2 个可复用模板
* 新工作流可从模板一键派生
* 模板修改不影响已派生工作流

### P0-8. 验收指标定义

你说的成功标准是“能支撑真实业务交付、发布后稳定运行、链路配置时间缩短”。这要转成可验收指标。

建议直接定成：

* 完成 1 条核心链路迁移
* 真实交付至少跑通 1 次
* 发布后配置可重复运行
* 同一链路配置时间比现状缩短 50%
* 新增常规节点不改核心架构

## P1：应该做，做完才像“平台雏形”

P1 的目标是：**让 Prism Editor 从“你自己能用”升级成“团队能复用”。** 你想让非开发者也能跑链路、沉淀标准化资产，这些都属于 P1 的平台补强。

### P1-1. 工作流版本管理

你未来一定会遇到：

* 模板升级
* 已发布配置回滚
* 不同业务版本并行

所以要补：

* 草稿版本
* 发布版本
* 回滚机制
* 版本备注

**完成标准：**

* 每次发布自动生成版本
* 可查看历史版本
* 可回滚到任一稳定版本

### P1-2. 最小运行能力抽象

虽然你说运行页先弱化，但不代表运行能力不重要。你的回答其实已经说明：发布物未来可能是页面、API、模块、模板快照或运行配置。P1 要做的，就是把这些统一成一个“运行协议”。

任务包括：

* 定义运行接口
* 支持以配置驱动执行
* 支持嵌入业务平台
* 支持最小 API 调用方式

**完成标准：**

* 同一个发布物可通过页面和接口两种方式消费
* 外部平台接入不需要知道编辑器内部状态

### P1-3. 节点注册机制

第一阶段不做开放插件，但要先把“未来可扩展”的门留出来。你已经明确后续会参考 ComfyUI 方向做插件机制。

任务包括：

* 节点 definition 注册协议
* 节点分类与分组
* 节点元数据规范
* 节点参数 schema 规范
* 节点兼容性约束

**完成标准：**

* 新增系统节点不需要改核心画布逻辑
* 节点定义方式统一
* 节点文档可自动生成基础信息

### P1-4. 模板中心 / 场景入口

你说首页目前就很好，那 P1 不是推翻首页，而是在现有结构上增强“模板和场景”这一层。

任务包括：

* 模板列表
* 按场景分类
* 搜索/筛选
* 最近使用
* 推荐模板

**完成标准：**

* 团队成员能快速找到合适模板
* 不再需要靠口头传递“你去复制某个工作流”

### P1-5. 基础权限与资产归属

你明确说第一阶段不做复杂权限系统，但这不代表完全不做权限。最小归属模型要有，不然后面版本、模板、节点都会乱。

建议只做最小三层：

* 作者
* 可查看/可运行者
* 管理者

**完成标准：**

* 工作流、模板、节点都有归属关系
* 至少能区分“谁能编辑、谁只能运行”

### P1-6. 执行日志与问题追踪

既然你担心稳定性和调试，那执行日志是 P1 必补项。

任务包括：

* 工作流执行记录
* 错误日志
* 节点耗时统计
* 输入输出摘要
* 失败重现信息

**完成标准：**

* 团队能追查某次运行为什么失败
* 能初步识别性能瓶颈节点

## P2：先预埋，不要现在做重

P2 的目标不是交付，而是**只在架构上留口，不在产品上大规模展开**。因为你长期明确想走对外 SaaS、节点生态抽成、定制化交付平台，但第一阶段如果提前冲这些，项目很容易失控。

### P2-1. 插件机制

现在先不做完整插件系统，只预留：

* 节点加载接口
* 节点包元信息结构
* 注册入口
* 安全边界占位

以后再做：

* 插件安装
* 插件启停
* 插件版本兼容
* 插件审核

### P2-2. 节点商城 / 上传分发

你已经想好了未来偏服务端注册、商城上传、平台抽成的模式。这个方向可以记进路线图，但现在不要把商城做成 P1。

现在只预留：

* Node Package 元数据模型
* 开发者信息字段
* 上架状态字段
* 审核状态字段

### P2-3. SaaS 多租户

未来如果真走 SaaS，这块一定要做，但现在不要提前做复杂：

* 租户模型
* 配额模型
* 订阅模型
* 结算模型

现在只建议预留：

* user / org / workspace 的命名空间概念

### P2-4. AI 自动搭建工作流

你提到未来可能做 AI 自动搭建工作流并收费。这个很有想象力，但必须建立在节点协议、模板体系、发布协议都稳定之后。

现在只需要预留：

* 工作流 JSON 可被生成
* 节点定义可被 LLM 读取
* 参数 schema 足够结构化

### P2-5. 通用非图像工作流

你长期相信“一切都可以是节点”，但第一阶段明确只做图像链路。那非图像工作流不要现在扩。

现在只做一件事：

* 保证核心契约别把自己写死成“只能处理某一种图像业务”

## 推荐开发顺序

如果按最稳的顺序排，我建议是：

**第一轮**

* P0-1 核心数据契约
* P0-3 最小系统节点集
* P0-4 编辑器最小闭环

**第二轮**

* P0-2 核心链路迁移
* P0-5 输入输出映射
* P0-6 最小调试能力

**第三轮**

* P0-7 模板机制
* P0-8 验收指标跑通

**第四轮**

* P1-1 版本管理
* P1-3 节点注册机制
* P1-6 执行日志

**第五轮**

* P1-2 运行协议
* P1-4 模板中心
* P1-5 基础权限归属

这样做的好处是：你先拿到一个真能用的编辑器，再补平台能力，而不是一开始就陷进生态幻想里。这个排序完全符合你当前“编辑器优先、运行页弱化、浏览器端为主、先支撑真实业务”的判断。
