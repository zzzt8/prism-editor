# Prism Editor 技术架构约束清单 v0.1

## 0. 总原则

### 0.1 第一原则：先收边界，再长功能

Prism Editor 现阶段不是通用工作流平台，而是 **图像链路编辑器 + 未来生态底座**。
所以任何新增能力都必须先回答三个问题：

1. 它是不是服务第一阶段的图像链路业务
2. 它属于编辑态、模板态还是发布态
3. 它会不会污染未来的开放能力边界

**结论：**

* 可以为未来留接口
* 不能为了未来，把现在的核心做乱

这和你自己定下来的方向完全一致：第一阶段先做内部图像链路复用和底层引擎，不做泛化平台。

---

## 1. 领域边界约束

### 1.1 第一阶段只允许“图像链路域”

第一阶段不做任意类型工作流，只做图像链路。
所以架构层必须默认：

* 输入以图像素材、图层参数、合成参数为主
* 输出以效果图、生产图、处理中间产物为主
* 节点优先围绕图像处理原语构建

**禁止：**

* 提前为非图像通用自动化做大量抽象
* 把一切业务流程都拉进 Prism

因为你已经明确说了第一阶段不做任意类型工作流，只做图像链路。

### 1.2 业务目标必须可回到真实链路

任何 P0/P1 功能，都要能映射到这条主链路：

**输入 → 抠图 / 缩放 / 遮罩 / 合成 / 导出 → 输出效果图与生产图纸。** 

如果一个功能不能让这条链路更稳定、更易搭建、更易复用、更易调试，它就不应该优先开发。

---

## 2. 数据模型约束

### 2.1 三态模型必须分离

系统中至少存在三种核心对象，禁止混用：

* **EditorDraft**：编辑中的工作流
* **Template**：可复用模板
* **PublishedConfig / RuntimeConfig**：发布后的运行配置

**硬约束：**

* 编辑态字段不能直接泄漏到发布态
* 模板不是草稿别名
* 发布物不能依赖编辑器本地 store 才能运行

### 2.2 核心对象必须版本化

以下对象必须带版本概念：

* workflow
* template
* node definition
* published config

**硬约束：**

* 任何破坏性字段调整都必须走版本升级
* 不允许无版本协议直接改 schema

### 2.3 输入输出 schema 必须显式声明

每个工作流都必须定义：

* 输入类型
* 输出类型
* 必填/选填
* 默认值
* 暴露参数
* 内部参数

**禁止：**

* 运行时靠 UI 猜输入结构
* 节点之间通过隐式约定传值
* 同一参数名在不同层含义不同

你已经明确说未来运行页可能弱化为 API 接口，因此 I/O 结构必须先干净。

---

## 3. 节点系统约束

### 3.1 节点不是 React 组件，节点是协议

节点在架构上必须至少拆成四层：

1. **NodeDefinition**：名称、分类、输入输出、参数 schema、能力描述
2. **NodeRuntime / Executor**：真正执行逻辑
3. **NodeInspectorSchema**：参数面板 schema
4. **NodeRenderer**：画布显示层

**禁止：**

* 把执行逻辑写进画布组件
* 把 UI 状态写进节点协议
* 一个节点文件同时管定义、执行、UI、状态存储

### 3.2 第一阶段只允许系统节点白名单

虽然你的长期理念是“一切都可以是节点”，但第一阶段必须只开系统节点白名单。

建议白名单只包括：

* Input
* Load Image
* Transform / Resize
* Mask / Apply Mask
* Composite
* Preview
* Export
* Output

**禁止：**

* 第一阶段直接做开放插件加载
* 未验证的业务节点进入核心系统节点层
* 系统节点和实验节点混在一个注册域里

### 3.3 节点必须无副作用优先

节点执行默认应趋向：

* 相同输入 → 相同输出
* 副作用最小
* 外部依赖显式声明

**允许例外：**

* Export
* Remote API
* AI 调用类节点

但例外节点必须显式标注 `sideEffect: true`。

### 3.4 节点新增不允许改核心

新增一个普通节点，理论上只应改：

* definition
* executor
* inspector schema
* registry entry

**禁止：**

* 每加一个节点就改画布核心
* 每加一个节点就改执行引擎主流程
* 每加一个节点就补特判

这是你未来能不能做成“节点平台”的第一条命门。

---

## 4. 执行引擎约束

### 4.1 第一阶段执行以浏览器端为主

这一点已经被你明确选定。

所以架构必须默认：

* 本地执行优先
* 发布物默认浏览器可跑
* 服务端执行只是未来扩展，不是当前基础依赖

### 4.2 执行图必须是有向无环图

P0/P1 阶段默认 DAG。
**禁止：**

* 先支持循环
* 先支持复杂条件分支
* 先支持事件驱动编排

原因很简单：你当前最大的风险是复杂度失控，不是表达力不够。

### 4.3 执行上下文必须标准化

每次运行都要有统一 `ExecutionContext`，至少包含：

* runId
* workflowVersion
* input payload
* node results
* timing
* error info
* cache scope

**禁止：**

* 节点私自读全局状态
* 执行过程直接耦合 UI store

### 4.4 发布态执行必须去编辑器依赖

发布出去的运行配置，不允许再依赖：

* React Flow 节点位置
* 编辑器草稿状态
* 面板临时状态
* 本地未保存变量

这点非常关键。否则你永远只有编辑器，没有真正的发布能力。

---

## 5. 状态管理约束

### 5.1 UI 状态与领域状态必须分离

至少拆成两层：

* **UI State**：选中节点、缩放、面板开关、拖拽状态
* **Domain State**：workflow graph、template、published config、execution result

**禁止：**

* 把 graph 真相放在 UI store 临时字段里
* 用一个超大 store 管一切

### 5.2 单一真相源

同一种核心数据，只允许有一个 source of truth。

例如：

* 当前工作流 graph 真相只在 domain store
* React Flow nodes 是 projection，不是真相

### 5.3 编辑器 projection 可丢失，领域数据不可丢失

节点位置、折叠状态、面板展开状态这类可以是编辑器 projection。
但节点连接、参数、输入输出定义不能依赖 projection 保存。

---

## 6. 发布与运行协议约束

### 6.1 “发布”必须统一语义

第一阶段不要求发布物只有一种形态，但发布动作必须统一定义为：

**从编辑态工作流生成可运行配置。**

可以映射成：

* 页面
* API
* 嵌入模块
* 模板快照

但底层都应该来自同一个发布协议。
这正对应了你说的“这些可能都有，要根据业务来”。

### 6.2 发布物必须稳定、可回滚、可审计

最低要求：

* 发布版本号
* 发布时间
* 发布人
* 来源模板/草稿
* 兼容 schema 版本

### 6.3 发布输入不得依赖作者知识

发布后可运行配置的输入结构，不能只有作者自己懂。
必须由系统显式生成说明和 schema。

---

## 7. 调试与可维护性约束

### 7.1 调试能力必须是架构能力，不是临时补丁

你已经把“调试体验差”和“全靠 AI 写代码未来不可维护”说得很明确了，所以调试不是锦上添花，而是核心架构项。

P0 就必须具备：

* 节点级输入快照
* 节点级输出快照
* 节点级报错
* 执行路径高亮
* 一键重跑

### 7.2 任何错误必须可定位到节点级

不接受：

* “执行失败”这种黑盒错误
* 只能在控制台找错误
* 只能靠猜是哪一步坏了

### 7.3 核心节点必须有样例和测试

每个系统节点至少要有：

* 最小输入样例
* 预期输出
* 异常输入样例

你最怕的是未来不可维护，那就必须让测试成为“第二理解层”。

---

## 8. 存储与持久化约束

### 8.1 数据持久化对象必须分层

至少分：

* workflow drafts
* templates
* published configs
* execution records

**禁止：**

* 用一个表/一个 JSON 把所有对象全塞进去
* 让模板和实例共享同一身份

### 8.2 本地存储只做缓存，不做真相

localStorage / IndexedDB 可以用于：

* 临时草稿缓存
* 最近打开记录
* UI 偏好

**禁止：**

* 把正式发布物真相只存在本地
* 把版本历史只放本地

### 8.3 导入导出只是迁移能力，不是主存储模型

JSON import/export 可以保留，但不能成为模板机制和发布机制的替代品。

---

## 9. 包结构与模块边界约束

### 9.1 Monorepo 包职责必须单一

建议长期固定成这样的边界：

* `shared-types`：纯类型与 schema
* `node-definitions`：节点定义协议
* `workflow-core`：执行引擎与 graph 处理
* `image-ops`：图像处理算法
* `dev-tool`：作者端编辑器
* `user-app`：运行端
* `server`：持久化、发布、权限、分发

### 9.2 shared-types 禁止反向长成杂物包

这是很多项目后期最容易炸的地方。

**禁止：**

* 在 `shared-types` 里放 store
* 在 `shared-types` 里放 UI helper
* 在 `shared-types` 里放业务逻辑

它只能承担：

* 类型
* schema
* 枚举
* 公共协议定义

### 9.3 dev-tool 不得吞掉运行时逻辑

编辑器是作者端，不是整个系统本体。
任何会被发布物复用的运行逻辑，都必须沉到 core 层，而不是留在 dev-tool。

---

## 10. API 与服务端边界约束

### 10.1 服务端第一阶段只承担平台职责

因为你选的是浏览器端执行为主，所以服务端当前职责应限于：

* 鉴权
* 存储
* 发布
* 版本
* 资产元数据
* 未来节点分发预留

**禁止：**

* 把服务端提前做成所有图像处理的主执行中心

### 10.2 服务端必须为未来生态预留命名空间

哪怕 P0 不做商城，也建议先预留：

* user
* org / workspace
* node package
* template package
* publish artifact

你后面想走 SaaS、抽成、商城，这些命名空间最好现在就别写死。

---

## 11. 安全与扩展约束

### 11.1 第一阶段不开放第三方执行权限

插件机制暂不开放，意味着：

* 不执行未知第三方代码
* 不引入动态远程 bundle 执行
* 不在浏览器直接加载不受控节点包

### 11.2 未来开放生态必须走“注册 + 审核 + 分发”

你已经偏向服务端注册和商城分发，而不是本地任意安装。那技术上就要避免先把自己做成“本地随便装脚本”的结构。

---

## 12. 性能约束

### 12.1 性能优化优先级低于结构稳定

第一阶段先别为了性能过早复杂化。
优先顺序应是：

1. 数据契约正确
2. 执行链路可调试
3. 节点新增不改核心
4. 再做缓存和性能优化

### 12.2 但要预埋基础性能钩子

建议预留：

* 节点执行耗时
* 简单 cache key
* 结果 memo
* 图像对象生命周期管理

因为图像链路一旦跑大，内存和重算一定会出问题。

---

## 13. UI 架构约束

### 13.1 UI 可以晚一点漂亮，但交互结构不能乱

你一方面说允许局部技术债，一方面又明确说 UI 也要好、图像处理 UI 要符合人习惯。这里我的解读是：

* 视觉可以渐进优化
* 但交互模型不能反复推翻

所以第一阶段必须先统一：

* 画布主区
* 参数面板
* 预览区
* 模板入口
* 调试入口

### 13.2 作者端 UI 优先于运行端 UI

因为你已经明确第一阶段是编辑器为主、运行页先弱化。
所以设计资源优先投到：

* 搭链效率
* 参数理解
* 节点可发现性
* 调试体验

而不是先把运行端做得很花。

---

## 14. 可接受的技术债 / 不可接受的技术债

### 可接受

* 局部 UI 不够精致
* 某些管理后台页面先粗糙
* 先不做完整权限
* 先不做复杂插件机制
* 个别非核心模块实现不够优雅

### 不可接受

* 核心数据契约混乱
* 节点定义和执行层耦合
* 编辑态/发布态不分
* 新增节点必须改核心
* 无法定位执行错误
* 发布物依赖编辑器本地状态

这正好对应你说的：允许一部分技术债，但核心数据契约必须先干净，架构必须稳。

---

## 15. 最终约束总结

如果把整份清单压缩成 8 条最重要的话，就是：

1. 第一阶段只做图像链路，不做泛化平台
2. 编辑态、模板态、发布态必须分离
3. 节点是协议，不是 UI 组件
4. 新增节点不得改核心
5. 浏览器端执行优先，服务端先做平台能力
6. 发布物必须去编辑器依赖
7. 调试能力必须节点级可见
8. 可以欠 UI 细节债，但不能欠核心结构债
