# Prism Editor PRD 初稿 v0.1

## 1. 项目名称

**Prism Editor**

## 2. 文档定位

本文档用于定义 Prism Editor 第一阶段的产品目标、用户范围、核心场景、功能边界、技术约束与阶段性里程碑，作为后续设计、开发、评审和任务拆解的基础。本文档聚焦 **第一阶段内部生产工具化**，不以开放生态为当前交付目标，但会为后续生态化预留架构方向。

---

## 3. 项目背景

当前图像处理与合成链路仍高度依赖手写代码、临时逻辑和个人经验，导致以下问题持续存在：

* 重复造轮子严重
* 链路难以复用和沉淀
* 非开发者很难直接使用复杂图像链路
* 当前整体稳定性不足，仍处于大量试错阶段
* 未来若继续仅靠 AI 辅助生成代码推进，维护成本与可控性存在明显风险。

Prism Editor 的诞生，不只是为了替代某一段图像处理代码，而是为了把“输入素材 → 图像处理链路 → 输出效果图/生产图”的过程，从一次性实现，升级为 **可编辑、可复用、可发布、可沉淀的系统能力**。长期来看，它希望成为一种网页化、可定制的图像处理工具底座，让没有 Photoshop 基础的人，也能完成复杂的图像处理与组合工作。

---

## 4. 产品定位

### 4.1 一句话定位

**Prism Editor 是一个面向内部团队的图像处理链路可视化编辑器，用于将效果图与生产图的合成流程模块化、模板化和标准化，并为未来开放节点生态预留底层能力。** 

### 4.2 第一阶段定位

第一阶段的 Prism Editor，优先是：

1. 一个给内部团队复用图像处理链路的工作流编辑器
2. 一个为未来节点生态做准备的底层引擎

而不是立刻成为一个对外开放的通用工作流平台。

### 4.3 长期愿景

长期目标不是只做内部工具，而是逐步成长为：

* 类似 n8n 的工作流平台化能力
* 类似 ComfyUI 的节点扩展生态
* 同时吸收 Figma 在作者端产品体验上的优点

最终可能形成 SaaS、节点分发抽成、定制化交付平台等商业模式。

---

## 5. 产品目标

## 5.1 第一阶段核心目标

第一阶段聚焦三个核心目标：

1. **减少重复造轮子**
   将常见图像链路从零散代码和临时逻辑中抽离出来，沉淀为可复用模板与节点组合。

2. **让非开发者也能运行链路**
   降低复杂图像流程的使用门槛，不要求使用者具备 Photoshop 或代码基础。

3. **沉淀标准化资产**
   让链路、模板、节点、输入输出结构逐步成为稳定资产，而不是只掌握在少数人手里的经验。

## 5.2 第一阶段不追求的目标

第一阶段不以“开放生态规模”“插件商城”“通用自动化平台”作为交付目标，也不追求覆盖所有类型工作流，而是只聚焦图像链路。

---

## 6. 目标用户

### 6.1 核心用户优先级

第一阶段目标用户优先级如下：

1. **链路作者**：搭建和维护工作流的人，当前主要是你自己
2. **内部设计师**：需要运行、复用或轻度调整工作流的人
3. **产品经理**：需要理解流程、协调链路和验收输出结果的人。

### 6.2 作者与使用者关系

作者与使用者在第一阶段 **并非完全割裂**。虽然大部分链路仍由少数人搭建，但部分使用者未来也可能基于自身需求搭建简单工作流。因此，产品在第一阶段应以“作者优先”设计，但模型上需允许“使用者向作者过渡”的可能性。你也明确提到，当前项目最初是为了减少自己图像合成纯代码的工作量，但未来希望它可以脱离具体业务平台，成为更通用的引擎。

---

## 7. 核心业务场景

### 7.1 第一条重点打磨链路

第一阶段最优先打磨的链路为：

**输入素材 → 抠图 / 缩放 / 遮罩 / 合成 / 导出 → 输出效果图与生产图纸 → 效果图发给用户 → 生产图发给厂家。** 

### 7.2 当前场景痛点

当前该链路的最大问题不是“有没有功能”，而是：

* 稳定性不足
* 仍处于试错开发早期
* 缺少足够可复用、可维护、可调试的产品化承载。

### 7.3 最终替代对象

Prism Editor 长期希望替代的不是单一工具，而是三类东西：

* Photoshop 中大量重复、机械的处理流程
* 依赖个人经验传承的图像处理方法
* 分散在脚本、网页、临时页面中的图像合成逻辑。

---

## 8. 产品形态

### 8.1 第一阶段产品形态

第一阶段产品形态为：

**编辑器为主，运行页先弱化。** 

原因是：当前最需要的是把链路搭建与复用能力做稳，而不是立刻把终端运行页做成完整独立产品。未来运行页很可能进一步抽象为 API 接口，先接入现有业务平台，等 Prism Editor 能力足够成熟后，再演进成更独立、更完整的面向用户的运行产品。

### 8.2 首页策略

当前首页方向可继续沿用，不在第一阶段进行大幅重构。

### 8.3 “发布”的定义

发布在第一阶段不强绑定为某一种产物，而应被统一定义为：

**将一个已验证的工作流，转换为某种业务可消费的运行配置。**

它未来可映射为：

* 用户页面
* 固定 schema 的 API
* 可嵌入业务系统的模块
* 模板快照
* 版本化运行配置。

---

## 9. MVP 范围

### 9.1 第一阶段必须具备的能力

基于你的回答，第一阶段 MVP 的核心能力为：

1. **节点编辑**
   支持用户通过可视化方式组织图像链路。

2. **参数面板**
   支持节点参数配置、修改与检查。

3. **预览**
   支持链路结果或关键中间结果预览。

4. **模板复用**
   支持把通用链路保存为可再次使用的模板。

5. **输入输出映射**
   支持定义工作流对外暴露的输入与输出。

### 9.2 我建议补入 P0 的隐含基础能力

虽然你没有把它们明确列入前五，但为了让上面的目标真正成立，第一阶段至少还需要两个“隐含 P0”：

* **保存草稿**：否则无法承载真实编辑器工作流
* **最小可用发布能力**：否则“模板复用”和“对外运行配置”无法闭环

这不是改变你的方向，而是为了让 MVP 真正可落地。这个补充是我基于你“已发布工作流可稳定运行”“运行页先弱化但未来可 API 化”的回答做的产品化收束。

---

## 10. 非目标范围

第一阶段明确不做：

* 复杂权限系统
* 任意类型工作流，只做图像链路
* 云端超大规模执行
* 开放安装第三方节点
* 在线 marketplace
* 多人实时协作。

这些能力都可能属于第二阶段或更后期，但如果现在同时推进，会严重稀释产品焦点，影响第一阶段闭环质量。这个结论是依据你对 MVP、非目标和长期愿景的组合回答做出的范围收束。

---

## 11. 节点系统策略

### 11.1 节点定义

从长期价值上，你希望“一切可复用的能力都可以是节点”。这是一种正确的生态哲学，因为做节点的本质，就是为了避免不断重复造轮子。

### 11.2 第一阶段节点边界

但在第一阶段，节点来源必须收紧：

* 以 **系统节点** 为主
* 先把图像处理核心链路所需的基础节点做稳
* 暂不开放外部插件机制
* 等系统节点足够稳定后，再引入插件机制，方向可参考 ComfyUI。

### 11.3 长期生态方向

长期来看，第三方节点接入更理想的方式偏向：

* 服务端注册
* 插件商城上传/审核/分发
* 平台托管式使用，而不是高度依赖本地安装。

---

## 12. 技术约束与架构原则

### 12.1 执行位置

第一阶段以 **浏览器端执行为主**。

### 12.2 当前最大的技术风险

你明确担心三个问题：

* 数据结构会越来越乱
* 节点系统会失控
* 调试体验差

并且你担心未来如果持续依赖 AI 写代码，项目可维护性可能不足。

### 12.3 第一阶段技术原则

因此第一阶段必须遵守以下原则：

1. **核心数据契约必须先干净**
   编辑态、模板态、发布态的数据结构不能继续混着长。

2. **架构必须稳**
   UI 可以逐步优化，但底层模型和边界不能反复摇摆。

3. **允许局部技术债，但不能污染核心契约**
   也就是可以先跑通业务，但不能在工作流定义、节点协议、输入输出模型上随意妥协。

4. **图像处理 UI 体验不能太粗糙**
   交互上需要遵循符合人使用习惯的原则，你希望它带有接近 Apple 风格的克制与顺手感。

---

## 13. 成功标准

第一阶段成功，至少应满足以下条件：

1. **能支撑真实业务交付**
2. **已发布工作流可稳定运行**
3. **链路配置时间明显缩短**。

为了后续管理更清晰，建议将其量化为：

* 至少完成 2–3 条核心图像链路迁移
* 至少 1 条链路支撑真实业务交付
* 链路搭建/复用时间缩短 50%
* 新增常规节点时不需要改动核心架构
* 发布后的运行配置可重复执行、结果稳定。

这里的量化部分是我在你原始成功标准基础上的补全，用于方便后续验收。原始目标来自你的回答，量化数字属于产品化建议。

---

## 14. 阶段性路线图

### 阶段 1：内部生产工具化

目标：把 1–3 条核心图像链路做成可编辑、可复用、可调试、可发布的内部工具。
重点：编辑器体验、模板沉淀、输入输出映射、最小发布能力、稳定性提升。

### 阶段 2：内部平台化

目标：把工作流从“你自己可用”推进到“团队可复用”。
重点：版本、模板中心、更多系统节点、最小权限分层、运行配置标准化。
这一步是基于你“让非开发者也能跑链路”和“沉淀标准化资产”的目标做出的自然延伸。

### 阶段 3：生态化与商业化

目标：从内部平台演进为外部开放能力。
可能路径：SaaS、节点抽成、定制化交付、插件商城、AI 辅助搭链路。
这一步基于你对对外 SaaS、节点生态抽成、定制化交付平台的判断。

---

## 15. 当前版本的关键开放问题

以下问题暂未完全定稿，但不阻塞第一阶段 PRD 生效：

1. “发布物”的统一协议到底长什么样
2. 模板与工作流实例的边界
3. 系统节点的最小集合
4. 浏览器端执行下的调试机制和性能边界
5. 未来 API 化时，输入输出映射的 schema 如何稳定
6. 节点商城与服务端注册机制未来如何设计。

---

## 16. 结论

Prism Editor 第一阶段，不是做一个“什么都能编排”的宏大平台，而是先成为一个 **内部图像链路编辑器与底层引擎**：它服务真实业务，降低重复劳动，沉淀标准资产，帮助非开发角色使用复杂图像链路，并以浏览器端执行为主，逐步为未来的开放节点生态和商业化铺路。
